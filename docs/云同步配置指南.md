# 云同步配置指南（Supabase）

> 目标：让玩家用 GitHub 账号登录后，战绩、收藏、阅读进度自动同步到云端，换设备登录同一个账号就能接上。
>
> 全程 **0 元**，你只需要做一次约 10 分钟的后台配置。代码那边已经全部写好了。

---

## 先搞清楚三件事

**1. 不配置也能正常用。**
`src/lib/cloud-config.ts` 里两个值留空时，整站自动降级为纯本地模式：加密档案、游客玩法、导出导入全部照旧，不会报任何错。所以你可以放心先把代码推上线，回头再配。

**2. anon key 放在前端是安全的。**
这是 Supabase 的官方设计。它只能做「匿名身份能做的事」，真正拦住别人的是数据库的行级权限策略（RLS）—— 每个用户只能读写 `user_id` 等于自己的那一行，伪造别人的 `user_id` 会被数据库直接拒绝。

**3. 绝不要用 service_role key。**
那个 key 能绕过所有权限。它只应该出现在服务端，永远不要填进这个前端项目。

---

## 第一步：建 Supabase 项目

1. 打开 https://supabase.com ，用 GitHub 账号登录（顺便就把账号体系打通了）
2. **New project**
3. 填三项：
   - **Name**：`sen-space`（随便写）
   - **Database Password**：点 Generate 生成，**存到密码管理器**（这个只用于直连数据库，站点用不到，但丢了很麻烦）
   - **Region**：选 **Southeast Asia (Singapore)** —— 离越南和国内都最近，延迟最低
4. 点 Create，等 1～2 分钟初始化

---

## 第二步：拿两个值

后台左侧 **Project Settings → API**（新版界面叫 **Settings → API Keys**）：

| 要复制的 | 长什么样 | 用在哪 |
|---|---|---|
| **Project URL** | `https://abcdefghijklmn.supabase.co` | 填 `SUPABASE_URL` |
| **anon / publishable key** | 一长串 `eyJhbGciOi...` 或 `sb_publishable_...` | 填 `SUPABASE_ANON_KEY` |

---

## 第三步：填进代码

打开 `src/lib/cloud-config.ts`，改成：

```ts
export const SUPABASE_URL = 'https://你的项目ref.supabase.co';
export const SUPABASE_ANON_KEY = '你复制的 anon key';
```

> 也支持用环境变量覆盖（`PUBLIC_SUPABASE_URL` / `PUBLIC_SUPABASE_ANON_KEY`），
> 但 anon key 本来就是要公开的，直接写在这里更省事，不用去配 Secrets。

---

## 第四步：建表

1. 后台左侧 **SQL Editor → New query**
2. 把 `docs/supabase-schema.sql` 整个文件粘进去
3. 点 **Run**

跑完最后那条自检查询会返回一行：`已开启RLS = true`、`策略数量 = 4`，就对了。

---

## 第五步：开启 GitHub 登录

这一步要来回搬两个值，别急。

### 5.1 在 GitHub 建一个 OAuth App

1. 打开 https://github.com/settings/developers → **OAuth Apps → New OAuth App**
2. 填：
   - **Application name**：`森 · SEN'S SPACE`
   - **Homepage URL**：`https://zhuluzhisen.github.io`
   - **Authorization callback URL**：`https://你的项目ref.supabase.co/auth/v1/callback`
     （注意是**你的 Supabase 项目地址**，不是博客地址，这是最容易填错的地方）
3. 点 Register，然后 **Generate a new client secret**
4. 记下 **Client ID** 和 **Client Secret**（Secret 只显示一次）

### 5.2 填进 Supabase

后台 **Authentication → Providers → GitHub**：

1. 打开 Enable
2. 粘贴 Client ID 和 Client Secret
3. Save

### 5.3 配跳转白名单

后台 **Authentication → URL Configuration**：

- **Site URL**：`https://zhuluzhisen.github.io`
- **Redirect URLs** 加两条：
  ```
  https://zhuluzhisen.github.io/**
  http://localhost:4321/**
  ```

不加白名单的话，登录完会被踢回首页且拿不到会话 —— 表现是「点了登录，回来还是未登录」。

## 第八步：稳定性加固（两个 Secret）

免费版有两个真实的坑，都能免费补掉。

### 8.1 防暂停（保活）

规则是**连续 7 天没有数据库活动就暂停**，暂停后所有请求返回 HTTP 540。

有个细节很多人踩：**Supabase 判定的是「有没有真的查到数据库」**。打 `/auth/v1/health` 或 `/rest/v1/` 根路径这种不触达 Postgres 的端点，会拿到 200 假绿灯，数据库照样被暂停。所以保活必须查一张真实的表。

`.github/workflows/keepalive.yml` 里已经写成了 `GET /rest/v1/player_state?select=user_id&limit=1`，会经过 PostgREST → Postgres → RLS，属于真实活动。返回 `[]`（空数组）是正常的 —— 查询执行了就算数。

**仓库 → Settings → Secrets and variables → Actions → New repository secret**，加两个：

| Name | Value |
|---|---|
| `SUPABASE_URL` | `https://你的项目ref.supabase.co` |
| `SUPABASE_ANON_KEY` | 你的 anon key（本来就会公开在前端，不敏感） |

工作流失败会变红并给出具体原因（401 = key 错、404 = 表没建、540 = 已被暂停），不会静默失败。

> ⚠️ 一个无法回避的限制：GitHub 的定时工作流在仓库**连续 60 天没有任何提交**后会被自动禁用，而且停跑时不会再通知你。所以「一年都不更新代码」的情况下保活会失效。顺手提交点东西，或者偶尔进 Actions 页看一眼，就能规避。

### 8.2 每日自动备份

免费版**没有可下载的备份，也没有时间点恢复**。这是比「暂停」更该担心的事 —— 暂停只是冻结，数据还在；误删才是真的没了。

`.github/workflows/backup.yml` 每天把整个 `player_state` 导成 JSON，作为 Actions 产物保留 90 天。要再配一个 Secret：

| Name | Value |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | 后台 Settings → API 里的 **service_role** key |

**为什么这里可以用 service_role**：它只跑在 GitHub 的服务器上，不进前端、不进仓库。但绝不要填进 `src/lib/cloud-config.ts` —— 那个会被打包到浏览器里。

没配这个 key 时备份工作流自动跳过，不会报红。

## 关于「要不要换个更稳的平台」

一句话结论：**不要为了稳定性自己写后端**。

- Cloudflare D1 确实「免费且永不暂停」（5GB、10 万行写/天），但换过去意味着要自己实现认证、会话、密码哈希 —— 这几样写错的概率远高于 Supabase 免费版被暂停的概率。
- 真正的稳定性来自三件事：**本地优先**（现在已经有了：云端挂了照样能玩，恢复后自动补推）、**保活**、**备份**。前八步做完，这三点都齐了。
- 如果哪天确实需要 SLA（比如站点有了商业价值），Supabase Pro 是 $25/月，付钱买的是「不会暂停 + 每日备份 + 邮件支持」，这是唯一确定的答案。

## 数据结构长什么样

一个用户一行，全部塞在 `data` 里：

```json
{
  "profile": { "name": "zhuluzhisen", "createdAt": 1762000000000 },
  "games": {
    "snake":    { "best": 128, "plays": 9,  "last": 96,  "at": 1762000000000 },
    "tetris":   { "best": 5400, "plays": 3, "lines": 42, "level": 4 },
    "2048":     { "best": 8192, "plays": 12 },
    "breakout": { "best": 2100, "plays": 5, "level": 3 }
  },
  "bookmarks": { "hello-world": 1762000000000 },
  "likes":     { "astro-notes": 1762000000000 },
  "reads":     { "hello-world": { "at": 1762000000000, "progress": 0.62 } }
}
```

**冲突怎么处理**：合并时最高分取大值、局数取大值，所以「离线玩了几局」再联网，不会被云端旧数据冲掉。同一秒在两台设备上各打一局，两边都会保留最高分。

## 排错对照表

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 面板里根本没有「用 GitHub 登录」 | 两个值没填或格式不对 | 检查 `cloud-config.ts`，URL 必须是 `https://xxx.supabase.co` |
| 报「云端表还没建好」 | 第四步没跑 | 去 SQL Editor 跑 `docs/supabase-schema.sql` |
| 报「表没暴露给 API」 | 2026-10-30 新规则 | Settings → API → Exposed schemas 勾上 `public` |
| 点了登录，回来还是未登录 | Redirect URL 没在白名单 | 按 5.3 加两条，注意结尾的 `/**` |
| 登录页报 `redirect_uri_mismatch` | GitHub 回调地址填错 | 必须是 `https://<ref>.supabase.co/auth/v1/callback` |
| 能登录，但数据不出现 | RLS 策略没生效 | 重跑 SQL，确认自检返回策略数量 4 |
| 隔几天第一次打开很慢 | 免费项目被暂停冷启动 | 按第八步配保活 |

## 以后想升级成「服务端也看不到」

现在是明文存储 + RLS 权限隔离，服务端技术上能看到数据内容。个人游戏战绩这个级别完全够用。

如果以后要存私密内容，升级路径是把 `src/lib/save-store.ts` 里 `cacheCloud()` / `syncDown()` 中间的 `cloudData` 换成密文包 —— 复用现有的 AES-GCM 那套，云端只存 `{iv, ct}`。因为所有读写都走 `store.get/set`，游戏和页面代码一行都不用改。

## 成本提醒

免费额度：500MB 数据库 / 5 万月活 / 5GB 流量。

一条存档约 1KB，就算 10 万玩家也只有 100MB 左右。**个人站永远碰不到上限**，而且免费额度超了是停服不是扣钱，不存在「一觉醒来被扣费」的风险。
